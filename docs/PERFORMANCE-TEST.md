# JMeter·Scouter 부하 시험

온라인 수업·평가 흐름을 JMeter로 반복 실행하고 Scouter로 요청별 응답시간, CPU, 메모리, SQL 시간을 함께 확인했습니다.

## 시험 구성

- CSV 데이터로 사용자별 세션 분리
- 로그인 이후 목록·상세·파일 요청을 실제 사용 순서로 배치
- 정적 리소스 포함 여부와 HTTP 압축 여부 비교
- 애플리케이션 스레드 수와 로그 레벨을 조합해 반복 측정
- JMeter의 평균·최대·오류율·처리량과 Scouter의 SQL·API 호출시간을 함께 확인

## 확인된 결과

보관된 ClassRoom 시험 결과의 요약입니다. 로컬 자원이 제한된 조건에서 측정한 값이므로 운영 서버 수용량으로 해석하지 않았습니다.

| 동시 사용자 | 요청 수 | 평균 응답시간 범위 | 오류율 범위 | 처리량 범위 |
|---:|---:|---:|---:|---:|
| 40명 | 400 | 639~826 ms | 0.00~0.17% | 38~45 req/s |
| 100명 | 1,000 | 2,290~3,128 ms | 6.87~9.06% | 26~34 req/s |

100명 조건에서 오류율이 증가한 원인은 단순히 스레드가 부족해서가 아니라 시험 서버의 CPU·메모리 한계와 스레드 설정이 맞지 않았기 때문으로 판단했습니다. 스레드를 늘릴수록 항상 빨라지지 않았고, 압축은 동시 처리량이 충분할 때 효과가 더 컸습니다. 로그 레벨 역시 I/O 부하에 영향을 주었습니다.

## 개선 판단

1. 스레드 수는 최대값이 아니라 서버 자원과 대기시간을 기준으로 결정합니다.
2. 평균만 보지 않고 최대 응답시간과 오류율을 함께 확인합니다.
3. Scouter에서 느린 요청을 찾은 뒤 SQL 시간과 외부 API 시간을 분리합니다.
4. 정적 리소스와 업무 API를 나눠 재시험해 병목 위치를 좁힙니다.
5. 변경 전·후에 같은 사용자 데이터와 동일한 시나리오를 사용합니다.

[공개용 JMeter 계획](../samples/performance/classroom-scenario.jmx)은 내부 주소, 계정, 시험 식별자를 제거하고 흐름만 남긴 예제입니다.
