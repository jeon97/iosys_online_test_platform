# 근거와 공개 예제 구분

담당 업무에 대한 본인 설명, 원본 Controller·Service·Mapper와 SVN 작업 사본의 수정 정보를 대조하였습니다. 현재 원격 SVN 변경 로그를 확보하지 못하였으므로 파일 전체의 최초 작성자·단독 개발 여부나 개인별 코드 비율을 단정하지 않습니다. 아래 설명은 담당 기능의 개발·수정 참여와 원본에서 확인한 처리 방식을 구분한 것입니다.

## 확인 결과

| 기능 | 원본에서 확인한 내용 | 공개 예제의 보완 또는 확인 한계 |
|---|---|---|
| 위원 자동 배정 | 전체 문항 수의 몫·나머지로 연속 구간 배정 | 기존 배정량을 고려한 최소 배정 위원 우선 선택은 기존 공개 예제의 추가 설계 |
| 계획 이관 | 기존 연결 확인과 분야·유형·문항의 트랜잭션 저장 | 불변 구성 객체와 저장소 인터페이스 분리 |
| 문항 반입 | 트랜잭션 안의 기존 목록 삭제·메타데이터 조회·등록 | 전체 사전 검증, 중복·빈 목록 거절 |
| 시험 상태·외부 API | 결과·판정 상태 변경, 인증·평가·오답노트 API 업무 범위 | 제출·변경 요청 ID 멱등성, 전체 소유권 재검증 규칙은 원본 적용 여부 미확인 |
| API 개수 | 본인 설명 약 30개, 보관 V1.2 명세 기준 제공 21개·사용 2개 | 두 집계의 기준이 같다고 보거나 차이를 내부 API로 단정하지 않음 |

## 공개 코드의 역할

공개 코드는 원본의 업무 흐름을 설명하기 위해 독립 작성하였습니다. 회사 소스·쿼리·실제 식별자·내부 주소·인증정보·업무 데이터를 포함하지 않습니다. 별도 설계 규칙이 포함된 기존 예제도 유지하되 실제 재직 중 구현한 사실과 구분하였습니다.

신규 사례의 입력·처리·예외는 [구현 사례 상세](CASE-STUDIES.md), 실행 범위는 [검증 결과](VALIDATION.md)에 정리하였습니다. 테스트는 공개 예제의 로직과 가짜 저장소 계약에 한정되며 회사 원본 시스템, 실제 DB·메시지 큐·기관 SSO·LLM 서버의 통합 검증 결과가 아닙니다.
